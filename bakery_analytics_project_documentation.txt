MCP-POWERED MULTI-AGENT BAKERY ANALYTICS SYSTEM Project Overview and
Technical Documentation ================================================

1. PROJECT OVERVIEW

-   Project name: MCP-Powered Multi-Agent Bakery Analytics System.
-   Project type: Multi-agent AI application for natural-language
    database analytics.
-   Objective: Allow business users to ask questions about bakery sales
    data in natural language, without manually writing SQL.
-   The system uses specialized AI agents to plan analysis, inspect a
    database, generate and execute SQL, interpret results, and produce a
    business report.
-   Example question: “Which store has the highest sales?”

2. PROBLEM STATEMENT

-   Traditional database analysis often requires users to understand SQL
    and database schemas.
-   Business users may not have the technical skills to write analytical
    queries.
-   The application translates business questions into a sequence of
    database-analysis tasks.
-   It returns interpreted findings in a structured report rather than
    requiring users to inspect raw SQL results.

3. DATASET AND DATABASE

-   Database: PostgreSQL 18.7.
-   Database name: bakehouse_db.
-   Main table: bakery_sales.
-   Dataset size: 8,763 records.
-   Number of columns used: 11.
-   Columns:
    -   product_id
    -   product_weight

    -   product_type

    -   store_id
    -   store_establishment_year

5. MULTI-AGENT DESIGN

The application contains four specialized agents.

5.1 Planner Agent - Receives the original business question. -
Decomposes the question into smaller analytical tasks. - Adds execution
status to each task. - Selects the next pending task. - Routes the
workflow towards the Database Agent when a pending task exists. - Routes
the workflow towards the Report Agent when all tasks are complete.

5.2 Database Agent - Retrieves the database schema through the MCP
inspect_schema tool. - Sends the schema and current task to the LLM. -
Generates a PostgreSQL SELECT query. - Executes the query through the
MCP execute_readonly_sql tool. - Stores the SQL query and structured
result in the shared workflow state.

5.3 Analyst Agent - Reads the latest database query result. - Interprets
the result in the context of the business question. - Produces business
findings. - Marks the corresponding task as completed. - Adds the
analysis to the shared state.

5.4 Report Agent - Receives the completed task analyses and
observations. - Consolidates the findings. - Generates the final
business report. - Returns the report as the workflow output.

6. LANGGRAPH WORKFLOW

-   The workflow is implemented using LangGraph StateGraph.
-   The graph begins at the Planner Agent.
-   A conditional router checks whether a pending task exists.
-   If a task exists:
    -   The workflow moves to the Database Agent.
    -   The Database Agent inspects the schema, generates SQL, and
        executes it through MCP.
    -   The workflow moves to the Analyst Agent.
    -   The Analyst updates the shared state and marks the task
        complete.
    -   Control returns to the Planner Agent.
-   If no pending task exists:
    -   The workflow moves to the Report Agent.
    -   The Report Agent generates the final report.
    -   The workflow reaches END.

Graph flow: START -> Planner Agent -> Conditional Router -> Pending task
exists: -> Database Agent -> MCP schema inspection -> LLM SQL generation
-> MCP SQL execution -> Analyst Agent -> Update shared state -> Return
to Planner Agent -> No pending task: -> Report Agent -> END

7. SHARED STATE

-   A BakeryState TypedDict is used to share information between graph
    nodes.
-   Main state fields:
    -   business_question: Original user question.
    -   tasks: List of decomposed tasks and their statuses.
    -   current_task: Task currently being processed.
    -   schema: Retrieved database schema.
    -   sql_queries: SQL queries generated during the workflow.
    -   query_results: Database results associated with tasks.
    -   task_analyses: Findings produced by the Analyst Agent.
    -   observations: Consolidated analytical observations.
    -   final_resolution: Resolution field in the current state
        structure.
    -   final_report: Final generated business report.
-   Each graph node reads relevant state fields and returns updates.
-   This allows intermediate results to be passed between agents through
    the graph.

8. MCP SERVER AND DATABASE TOOLS

-   The MCP server exposes database functionality as tools.
-   The MCP client discovers available tools and invokes them from the
    application.
-   Tools registered in the project include:
    -   inspect_schema:
        -   Retrieves database and table schema information.
    -   execute_readonly_sql:
        -   Executes permitted read-only SQL and returns structured
            results.
    -   summarize_results:
        -   Provides result summarization functionality.
    -   Reporting tool:
        -   Provides report-related functionality.
-   The current LangGraph database execution path explicitly calls
    inspect_schema and execute_readonly_sql.
-   The final business report is generated by the Report Agent.

9. DATABASE SAFETY

-   SQL generated by an LLM is treated as untrusted input.
-   The read-only SQL tool is designed to:
    -   Allow SELECT and WITH queries.
    -   Reject semicolons to prevent multiple SQL statements.
    -   Execute queries in a read-only transaction.
    -   Return structured results or an error response.
-   These checks provide a safety layer independent of the LLM prompt.
-   Further production hardening could include database least-privilege
    permissions, query timeouts, row limits, and stronger SQL
    validation.

12. KEY ENGINEERING DECISIONS

-   Multi-agent design:
    -   Separates planning, database interaction, analysis, and
        reporting responsibilities.
-   LangGraph:
    -   Supports stateful execution, conditional routing, and repeated
        task processing.
-   MCP:
    -   Separates database tools from the agent orchestration code.
    -   Provides a standardized tool interface that can be reused by
        compatible clients.
-   Shared state:
    -   Maintains task status and intermediate outputs across agent
        executions.
-   Read-only database access:
    -   Reduces the risk of destructive SQL operations.
-   LangSmith:
    -   Makes it possible to inspect agent runs, tool calls, latency,
        and token usage.
